하네스란 무엇인가

이 장을 마치면: 하네스의 정의와 범위를 말할 수 있고, 프롬프트·컨텍스트·하네스 엔지니어링의 차이를 설명할 수 있으며, "실수는 하네스 버그"라는 사고방식을 갖추게 됩니다.

모델을 뺀 나머지 전부

LLM 자체는 토큰을 받아 토큰을 내놓는 함수입니다. 파일을 읽지도, 테스트를 돌리지도, 어제 한 일을 기억하지도 못합니다. 이 함수를 반복 호출하고, 도구를 실행해 결과를 돌려주고, 무엇을 보여줄지 고르고, 무엇을 못 하게 막고, 결과가 맞는지 확인하는 소프트웨어 전체가 하네스(harness)입니다. 하네스 엔지니어링은 이 실행 환경을 의도적으로 설계하고 계속 진화시키는 분야입니다.

용어 자체는 2026년 2월에 퍼졌습니다. Terraform 공동 창시자 Mitchell Hashimoto가 코딩 에이전트가 실수할 때마다 다시 지시하는 대신 환경에 영구적인 수정을 넣는 습관을 "engineering the harness"라고 불렀고, 곧이어 OpenAI와 Anthropic이 같은 생각을 확장한 엔지니어링 글을 냈습니다. 특히 OpenAI Codex 팀은 엔지니어 3명이 5개월 동안 사람이 직접 쓴 코드 없이 약 100만 줄 규모의 제품을 만들었다고 보고했는데, 초반이 예상보다 느렸던 이유를 모델 능력이 아니라 환경이 충분히 정의되지 않았기 때문이라고 진단했습니다.

하네스의 네 가지 기능

OpenAI의 정리를 빌리면 하네스는 에이전트를 제약(Constrain)하고, 할 일을 알려주고(Inform), 제대로 했는지 검증(Verify)하고, 틀렸을 때 교정(Correct)합니다. 이 책의 Part II는 Inform, Part III는 Constrain·Verify·Correct를 다룹니다.

핵심 사고방식: 실수는 하네스 버그다

에이전트가 같은 실수를 반복할 때 초보자는 채팅창에 "그거 하지 말라고 했잖아"를 입력합니다. 하네스 엔지니어는 질문을 바꿉니다. 어떤 능력이 빠져 있었고, 그걸 어떻게 보이게 하고 강제할 수 있을까? 그리고 그 답을 문서, 도구, 린터, 테스트, 권한 규칙 중 하나로 환경에 새겨 넣습니다. 이렇게 하면 수정이 누적됩니다. 오늘 고친 실수는 내일의 모든 세션에서 다시 일어나지 않습니다.

안쪽 하네스와 바깥쪽 하네스

  • 안쪽(inner) 하네스: 에이전트 제품 자체에 내장된 루프, 기본 도구, 컨텍스트 관리, 권한 체계. Claude Code나 Codex CLI 같은 도구가 기본으로 제공합니다. 에이전트를 직접 만들면 이 부분까지 설계합니다.
  • 바깥쪽(outer) 하네스: 그 제품 위에 프로젝트가 얹는 것. AGENTS.md 같은 지침 파일, 커스텀 린터와 테스트, 훅, 스킬, 관측 스택, CI 게이트. 대부분의 팀이 실제로 손대는 영역입니다.

두 층의 원리는 같습니다. 이 책은 원리를 안쪽 하네스를 직접 만들면서 익히고(2·3·11장), 그 감각을 바깥쪽 하네스 운영에 적용하는(6·7·10장) 순서로 진행합니다.

에이전트 루프

이 장을 마치면: 에이전트 루프를 직접 작성하고, 메시지 배열이 어떻게 자라는지 설명하며, 종료 조건과 무한 루프 방지를 설계할 수 있습니다.

전부 이 while 문에서 시작한다

모든 에이전트의 심장은 놀라울 만큼 단순합니다. 모델을 호출하고, 응답에 도구 호출이 있으면 실행하고, 결과를 대화에 붙여 다시 호출합니다. 도구 호출이 없으면 끝납니다. 아래 코드는 특정 SDK의 세부 사항을 걷어낸 최소 형태입니다.

agent_loop.py
def run_agent(task: str, tools: dict, max_turns: int = 30) -> str:
    # The conversation is the agent's entire working memory.
    messages = [{"role": "user", "content": task}]

    for turn in range(max_turns):
        response = call_model(
            system=SYSTEM_PROMPT,
            messages=messages,
            tools=[t.schema for t in tools.values()],
        )
        messages.append({"role": "assistant", "content": response.content})

        tool_calls = [b for b in response.content if b.type == "tool_use"]
        if not tool_calls:
            # No tool request means the model believes it is done.
            return response.text

        results = []
        for call in tool_calls:
            try:
                output = tools[call.name].run(**call.input)
                results.append(tool_result(call.id, output))
            except Exception as e:
                # Errors are feedback, never a crash: return them to the model.
                results.append(tool_result(call.id, f"ERROR: {e}", is_error=True))

        # Every tool_use id must be answered by a matching tool_result.
        messages.append({"role": "user", "content": results})

    return "Stopped: max_turns reached"

세 가지를 기억하세요. 첫째, 모델은 상태가 없습니다. 매 호출마다 messages 전체를 다시 읽습니다. 둘째, 도구 결과는 다음 입력이 되므로 토큰이 매 턴 누적됩니다. 셋째, 예외도 결과입니다. 하네스가 죽으면 에이전트는 배울 기회를 잃습니다.

종료 조건 설계

"도구 호출이 없으면 끝"은 모델의 자기 판단에 종료를 맡기는 것입니다. 실전 하네스는 여러 겹의 종료 조건을 둡니다.

조건목적구현 메모
자연 종료 (end_turn)정상 완료단독으로 믿지 말 것. 검증 게이트와 묶는다
최대 턴폭주 방지 (워치독)작업 유형별로 다르게. 도달 시 상태를 저장하고 멈춘다

벽시계 타임아웃행(hang) 방지도구 단위 타임아웃과 전체 타임아웃을 분리

loop_guard.py
import hashlib, json
from collections import Counter

class LoopGuard:
    """Detects the agent repeating the same action with the same arguments."""

    def __init__(self, limit: int = 3):
        self.limit = limit
        self.seen = Counter()

    def check(self, name: str, args: dict) -> str | None:
        key = hashlib.sha1(f"{name}:{json.dumps(args, sort_keys=True)}".encode()).hexdigest()
        self.seen[key] += 1
        if self.seen[key] >= self.limit:
            # Do not silently block; tell the model what is happening and what to try.
            return (f"You have called {name} with identical arguments "
                    f"{self.seen[key]} times and the result has not changed. "
                    "Stop and reconsider: read the last error carefully, "
                    "try a different approach, or report what is blocking you.")
        return None
흔한 함정
  • tool_result 누락: 병렬 도구 호출 중 하나만 결과를 돌려주면 대부분의 API가 다음 요청을 거부합니다. 실패해도 결과는 반드시 짝을 맞춥니다.
  • 도구 결과 무제한 주입: 10MB 로그를 그대로 넣으면 한 번에 컨텍스트가 망가집니다. 4장의 자르기·요약·파일 오프로드를 적용하세요.
  • 재현 불가능한 실행: 모든 모델 입출력과 도구 입출력을 기록하지 않으면, 실패를 디버깅할 수 없습니다(8장).

도구 설계: 에이전트-컴퓨터 인터페이스

이 장을 마치면: 모델이 잘못 쓰기 어려운 도구를 설계하고, 도구 출력을 토큰 효율적으로 만들며, 에러 메시지를 교정 신호로 활용할 수 있습니다.

사람에게 좋은 UI/UX가 필요하듯, 에이전트에게는 좋은 ACI(Agent-Computer Interface)가 필요합니다. 도구 이름, 설명, 파라미터, 출력 형식, 에러 메시지 하나하나가 모델의 행동을 바꿉니다. 같은 모델이라도 도구 설계에 따라 성공률이 크게 달라집니다.

여섯 가지 설계 원칙

  1. 작업 단위로 묶어라. list_files, open_file, filter_lines를 따로 주기보다 에이전트가 실제로 하려는 일(search_logs(service, level, since))에 맞춘 도구가 턴과 토큰을 아낍니다. API 엔드포인트를 1:1로 감싸는 것은 대개 나쁜 설계입니다.
  2. 설명은 신입 동료에게 쓰는 문서처럼. 무엇을 하는지, 언제 쓰고 언제 쓰지 말아야 하는지, 파라미터의 형식과 예시를 적습니다. 모델은 이 설명만 보고 판단합니다.
  3. 실수하기 어렵게(poka-yoke). 상대 경로 대신 절대 경로를 요구하고, 자유 문자열 대신 enum을 쓰고, 위험한 조합은 스키마 단계에서 막습니다.
  4. 출력은 짧고 의미 있게. 기본값은 요약, 필요할 때만 상세. 페이지네이션과 잘림 표시를 넣고, 잘렸다면 어떻게 더 볼 수 있는지 힌트를 줍니다. 내부 UUID보다 사람이 읽을 수 있는 이름을 반환합니다.
  5. 에러는 다음 행동을 알려줘라. Error 400이 아니라 "date는 YYYY-MM-DD 형식이어야 합니다. 받은 값: 11/05/2026"처럼 고치는 방법을 담습니다.
  6. 부작용을 분리하라. 읽기 전용 도구와 변경 도구를 나누고, 변경 도구에는 dry_run이나 멱등성 키를 둡니다. 7장의 권한 정책이 이 구분 위에서 작동합니다.

범용 셸 vs 전용 도구

강력한 모델에게 bash 하나만 줘도 상당히 많은 일을 합니다. 범용성이 높고, 모델이 이미 학습한 CLI 지식을 그대로 활용합니다. 대신 통제와 관측이 어렵습니다. 실무에서는 섞어 씁니다.

  • 셸: 탐색, 빌드, 일회성 스크립트. 샌드박스 안에서 넓게 허용.
  • 전용 도구: 자주 쓰는 작업(파일 편집, 검색), 위험하거나 감사가 필요한 작업(배포, DB 쓰기), 출력 형식을 통제해야 하는 작업.
  • 코드를 도구로: 수십 번 도구를 부르는 대신, 에이전트가 스크립트를 작성해 한 번에 실행하게 하면 중간 결과가 컨텍스트를 거치지 않아 효율적입니다.

도구를 외부 서비스와 표준 방식으로 연결하는 프로토콜이 MCP(Model Context Protocol)입니다. MCP는 연결 방법을 표준화할 뿐, 위의 설계 원칙을 대신해 주지는 않습니다. MCP 서버를 붙일 때도 도구 수와 설명 품질을 같은 기준으로 검토하세요.

실전 팁

도구를 만들었으면 에이전트에게 그 도구로 실제 과제 10개를 풀게 하고 트레이스를 읽으세요. 잘못된 인자, 불필요한 반복 호출, 무시된 출력 필드가 보이면 그게 다음 수정 대상입니다. 에이전트에게 트레이스를 주고 도구 설명을 개선하게 하는 것도 효과적입니다.

에이전트를 위한 에러 메시지

커스텀 린터의 진짜 가치는 메시지에 있습니다. 위반을 알리는 데서 그치지 않고 고치는 방법을 담으면, 에러 메시지가 곧 컨텍스트 주입이 됩니다. 필요한 순간에만 나타나는 가장 효율적인 문서입니다.

check_layers.py
import ast, pathlib, sys

# Allowed import direction: domain -> (nothing), app -> domain, infra -> app/domain
FORBIDDEN = {"domain": ("infra", "app"), "app": ("infra",)}

def check(root="src"):
    errors = []
    for path in pathlib.Path(root).rglob("*.py"):
        layer = path.relative_to(root).parts[0]
        for node in ast.walk(ast.parse(path.read_text())):
            if isinstance(node, ast.ImportFrom) and node.module:
                target = node.module.split(".")[0]
                if target in FORBIDDEN.get(layer, ()):
                    errors.append(
                        f"{path}:{node.lineno}: '{layer}' must not import '{target}'.\n"
                        f"  WHY: domain logic must stay testable without ROS/DDS.\n"
                        f"  FIX: define a Protocol in {layer}/ports.py and inject the "
                        f"implementation from infra/ at wiring time (see docs/architecture.md#ports)."
                    )
    return errors

if __name__ == "__main__":
    errs = check()
    print("\n".join(errs) or "layer check: OK")
    sys.exit(1 if errs else 0)

수정의 사다리

실수를 발견했을 때 어느 수준에서 고칠지 고르는 것이 하네스 엔지니어의 핵심 판단입니다. 위로 갈수록 내구성이 높지만 비용도 듭니다.

L0이번 대화에서 다시 지시한다. 이번 한 번만 해당하는 제약이면 이게 맞다.
L1AGENTS.md나 docs/에 적는다. 몰라서 틀린 경우.
L2도구나 환경을 추가한다. 확인할 수단이 없어서 틀린 경우.
L3린터·테스트·훅으로 기계적으로 막는다. 알면서도 반복되는 경우.
L4구조적으로 불가능하게 만든다. 권한, 샌드박스, 타입. 한 번이라도 일어나면 안 되는 경우.

확률적 규칙과 결정적 규칙

"프로덕션 DB는 건드리지 마"를 프롬프트에 쓰면 대부분 지켜집니다. 대부분. 안전 경계는 모델의 순응에 기대지 말고 코드로 구현합니다. 프롬프트는 의도를 알려주고, 하네스는 경계를 강제합니다.

  • 샌드박스: 컨테이너나 VM, 마운트된 디렉터리만 쓰기 가능, 네트워크는 허용 목록. 비밀 정보는 아예 마운트하지 않습니다.

프롬프트 인젝션과 치명적 삼요소

에이전트가 읽는 웹 페이지, 이슈 본문, 이메일, 파일 안의 텍스트는 데이터이지 명령이 아닙니다. 하지만 모델은 둘을 완벽히 구분하지 못합니다. Simon Willison은 다음 세 가지가 한 에이전트에 동시에 있으면 데이터 유출 공격이 가능해진다고 정리했습니다(lethal trifecta).

  1. 비공개 데이터에 대한 접근
  2. 신뢰할 수 없는 콘텐츠에 노출
  3. 외부로 정보를 보낼 수 있는 통로

방어의 핵심은 셋 중 하나를 구조적으로 끊는 것입니다. 웹을 읽는 에이전트라면 외부 전송을 막고, 외부로 보내야 하는 에이전트라면 비밀 정보를 주지 않습니다. 모델에게 "인젝션을 무시하라"고 부탁하는 것은 방어가 아닙니다.

pass@k는 "k번 중 한 번이라도 성공"으로, 사람이 결과를 골라 쓸 수 있는 상황에 맞습니다. pass^k는 "k번 모두 성공"으로, 매번 믿고 맡겨야 하는 자동화의 신뢰성 지표입니다. 위 계산은 시행이 독립이라고 가정합니다. 실제로는 어려운 과제에서 실패가 몰리므로 직접 측정해야 합니다.

import json, statistics

def run_suite(tasks, harness, trials=5):
    report = []
    for task in tasks:
        results = [harness.run(task["prompt"], workdir=task["fixture"]) for _ in range(trials)]
        passed = [task["grader"](r) for r in results]   # deterministic grader first
        report.append({
            "id": task["id"],
            "pass_rate": sum(passed) / trials,
            "pass_all": all(passed),
            "median_cost": statistics.median(r.cost for r in results),
            "median_turns": statistics.median(r.turns for r in results),
        })
    return report

# Gate in CI: a harness change must not regress the suite.
def gate(new, baseline, tolerance=0.03):
    mean = lambda rep: sum(t["pass_rate"] for t in rep) / len(rep)
    return mean(new) >= mean(baseline) - tolerance

멀티 에이전트의 가장 큰 이점은 "협업"보다 컨텍스트 격리입니다. 서브에이전트가 파일 50개를 뒤지고 로그 수천 줄을 읽어도, 메인 에이전트에게는 요약 몇 줄만 돌아옵니다. 메인 컨텍스트는 깨끗하게 유지되고 결정에 집중할 수 있습니다. 그 밖의 이점은 병렬성, 역할 특화, 독립적인 검토입니다.

에이전트는 패턴을 복제한다

에이전트는 코드베이스에 이미 있는 패턴을 따라 합니다. 좋은 패턴도, 나쁜 패턴도. 사람이 직접 쓰지 않는 코드베이스에서는 이 복제 속도가 빨라서 작은 일탈이 금세 퍼집니다. Codex 팀은 이를 관리하기 위해 제품 도메인과 아키텍처 계층별로 품질 등급을 매기는 문서를 유지하고, 주기적으로 도는 정리 에이전트가 일탈을 찾아 리팩터링 PR을 올리게 했습니다. 가비지 컬렉션을 사람이 아니라 하네스가 하는 것입니다.

덜어낼 수 있게 만들어라

하네스의 상당 부분은 현재 모델의 약점을 보완하는 비계(scaffolding)입니다. 모델이 좋아지면 그 비계는 도움이 아니라 방해가 됩니다. 과도한 단계 분할, 지나치게 상세한 지시, 불필요한 확인 단계가 더 똑똑한 모델의 판단을 묶습니다. 그래서 하네스 구성요소는 독립적으로 끄고 켤 수 있게 만들고, 모델이 바뀔 때마다 제거 실험(ablation)을 합니다. 하나씩 끄고 평가 세트를 돌려, 성능이 떨어지지 않으면 지웁니다.

원칙

제약과 검증(테스트, 권한, 샌드박스)은 모델이 좋아져도 남습니다. 지시와 절차(단계별 프롬프트, 하드코딩된 워크플로)는 모델이 좋아질수록 줄어듭니다. 앞의 것에 투자하고, 뒤의 것은 가볍게 유지하세요.

         {"path": {"type": "string"}, "old": {"type": "string"}, "new": {"type": "string"}}, ["path", "old", "new"]),
    tool(search, "grep -rn over *.py files. Use to find definitions and usages.",
         {"pattern": {"type": "string"}}, ["pattern"]),
    tool(run_tests, "Run pytest. Optional target like tests/test_parser.py::test_x.",
         {"target": {"type": "string"}}, []),
]]
SCHEMAS = [s for _, s in TOOLS.values()]


# ---------- policy and verification ----------
def permit(name: str, args: dict) -> str | None:
    if name == "replace_in_file" and args.get("path", "").startswith(("tests/", "./tests/")):
        # Blocks the classic shortcut of making tests pass by editing the tests.
        return "Editing tests is not allowed. Fix the code under src/ so the existing tests pass."
    return None


def verify() -> tuple[bool, str]:
    out = run_tests()
    return out.startswith("exit=0"), out


# ---------- loop ----------
def main(task: str) -> str:
    messages = [{"role": "user", "content": task}]
    guard, used = LoopGuard(limit=3), 0

    for turn in range(MAX_TURNS):
        resp = client.messages.create(model=MODEL, max_tokens=4096, system=SYSTEM,
                                      tools=SCHEMAS, messages=messages)
        used += resp.usage.input_tokens
        trace(kind="llm", turn=turn, in_tok=resp.usage.input_tokens,
              out_tok=resp.usage.output_tokens, stop=resp.stop_reason)
        messages.append({"role": "assistant", "content": resp.content})

        if resp.stop_reason != "tool_use":
            ok, out = verify()                    # never trust "I'm done" on its own
            trace(kind="gate", passed=ok)
            if ok:
                return "DONE"
            messages.append({"role": "user", "content":
                "The harness ran the full test suite and it still fails:\n"
                f"{cap(out)}\nKeep working until it passes."})
            continue

        results = []
        for block in resp.content:
            if block.type != "tool_use":
                continue
            t0 = time.time()
            blocked = permit(block.name, block.input) or guard.check(block.name, block.input)
            if blocked:
                out, err = blocked, True
            else:
                try:
                    out, err = cap(str(TOOLS[block.name][0](**block.input))), False
                except Exception as e:
                    out, err = f"ERROR: {type(e).__name__}: {e}", True
            trace(kind="tool", name=block.name, args=block.input, error=err,
                  ms=int((time.time() - t0) * 1000))
            results.append({"type": "tool_result", "tool_use_id": block.id,
                            "content": out, "is_error": err})
        messages.append({"role": "user", "content": results})

        if used > MAX_INPUT_TOKENS:
            trace(kind="stop", reason="budget")
            return "STOPPED: token budget exceeded"

    trace(kind="stop", reason="max_turns")
    return "STOPPED: max turns reached"


if __name__ == "__main__":
    print(main(sys.argv[1] if len(sys.argv) > 1 else "Make the test suite pass."))
