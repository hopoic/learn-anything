Part I · 기초 — 1장

복잡도와 비용 모델

이 장을 마치면: 코드의 시간·공간 복잡도를 빅오로 말할 수 있고, 입력 크기에 따라 어떤 알고리즘이 현실적인지 어림할 수 있으며, 같은 빅오 안에서 캐시와 메모리 배치가 만드는 수십 배 차이를 설명할 수 있습니다.

빅오는 증가율이지 속도가 아니다

알고리즘의 비용을 초 단위로 말하면 CPU, 컴파일러, 입력에 따라 값이 달라집니다. 그래서 입력 크기 n이 커질 때 연산 횟수가 어떻게 늘어나는지만 남기고 나머지는 버립니다. 이것이 점근 표기법입니다.

  • O(f(n)): 상한. 충분히 큰 n에서 비용이 c·f(n)을 넘지 않습니다. 실무에서 "빅오"라고 하면 보통 최악의 경우 상한을 뜻합니다.
  • Ω(f(n)): 하한. 어떤 알고리즘도 이보다 빠를 수 없다는 주장에 씁니다(7장의 비교 정렬 n log n 하한).
  • Θ(f(n)): 상한과 하한이 같을 때. "정확히 이 차수"라는 뜻입니다.

계산 규칙은 두 가지면 충분합니다. 상수 배는 버리고(3n² → n²), 가장 빨리 자라는 항만 남깁니다(n² + 100n → n²). 루프가 중첩되면 곱하고, 차례로 놓이면 더합니다. 반으로 줄여가는 루프는 log n입니다.

상수가 승부를 가른다: 메모리 계층

빅오는 모든 기본 연산의 비용을 같다고 가정합니다. 실제 CPU에서는 그렇지 않습니다. 데이터가 어느 캐시 계층에 있느냐에 따라 같은 "읽기 한 번"의 비용이 백 배 가까이 차이 납니다.

L2 캐시약 3–5ns. 코어당 수백 KB~수 MB.

수치는 최근 서버·데스크톱 CPU의 대략적인 자릿수입니다. 정확한 값은 칩마다 다릅니다.

CPU는 메모리를 64바이트 단위의 캐시 라인으로 가져오고, 순차 접근을 감지하면 다음 라인을 미리 가져옵니다(prefetch). 그래서 연속 배열을 훑는 O(n)과 포인터를 따라가는 O(n)은 같은 빅오지만 전혀 다른 속도로 달립니다.

임베디드 엔지니어의 눈으로

BSP와 드라이버를 해본 사람에게 이건 낯설지 않은 이야기입니다. DMA 버퍼를 캐시 라인에 정렬하고, ISR에서 접근하는 구조체를 한 라인에 몰아넣는 이유와 같습니다. 자료구조 선택은 결국 메모리에 무엇을 어떤 순서로 놓을 것인가의 문제이고, 빅오는 그 결정의 절반만 말해 줍니다.

분할 상환, 평균, 그리고 최악의 경우

복잡도를 말할 때는 어떤 경우를 말하는지 밝혀야 합니다.

  • 최악(worst case): 어떤 입력에서도 이보다 나쁘지 않다. 실시간 시스템이 신경 쓰는 값.
  • 평균(average case): 입력 분포를 가정한 기댓값. 해시 테이블의 O(1)은 "해시가 잘 퍼진다"는 가정 위의 평균입니다.
  • 분할 상환(amortized): 연산을 길게 이어서 했을 때 한 번당 평균 비용. 확률 가정이 없다는 점에서 평균과 다릅니다. 동적 배열의 push_back은 가끔 O(n) 재할당이 일어나지만, n번 연속 수행한 총비용이 O(n)이므로 분할 상환 O(1)입니다(2장).
흔한 함정

분할 상환 O(1)은 "매번 O(1)"이 아닙니다. 1kHz 제어 루프 안에서 push_back이 재할당을 일으키면, 그 한 주기만 수 밀리초가 걸려 데드라인을 놓칠 수 있습니다. 실시간 경로에서는 미리 reserve()하거나 고정 크기 구조(링 버퍼, 풀)를 씁니다. 이것이 WCET(최악 실행 시간) 관점입니다.

측정은 이렇게 한다

빅오로 후보를 추리고, 최종 결정은 측정으로 합니다. 측정 코드가 틀리면 결론도 틀립니다. 네 언어 모두 원칙은 같습니다. 단조 시계(monotonic clock)를 쓰고, 최적화 빌드로 재고, 결과를 사용해서 컴파일러가 루프를 지우지 못하게 하고, 여러 번 돌려 최솟값이나 중앙값을 봅니다.

배열, 동적 배열, 링 버퍼

이 장을 마치면: 동적 배열이 왜 분할 상환 O(1)인지 증명할 수 있고, std::vector와 같은 원리의 컨테이너를 직접 구현하며, 인터럽트와 태스크 사이에서 쓰는 락-프리 링 버퍼를 작성할 수 있습니다.

연속 메모리는 가장 강력한 자료구조다

배열의 i번째 원소 주소는 base + i × sizeof(T)입니다. 곱셈 한 번과 덧셈 한 번이므로 임의 접근이 O(1)입니다. 1장에서 본 것처럼 순회도 캐시가 가장 좋아하는 패턴입니다. 대가는 중간 삽입·삭제입니다. 뒤쪽 원소를 전부 한 칸씩 밀어야 하므로 O(n)입니다.

동적 배열: 두 배씩 키우면 평균 O(1)

크기를 미리 모를 때는 공간이 꽉 차면 더 큰 버퍼를 새로 잡고 기존 원소를 옮깁니다. 핵심은 얼마나 키우느냐입니다.

  • 매번 고정 크기(+k)만 늘리면: n번 push에 이동이 k + 2k + 3k + … ≈ n²/(2k)번. 전체 O(n²), 한 번당 O(n).
  • 매번 r배(r > 1)로 늘리면: 이동 횟수가 n/r + n/r² + … ≤ n/(r−1)인 등비급수. 전체 O(n), 한 번당 분할 상환 O(1).

아래 구현은 std::vector의 핵심만 남긴 것입니다. 원시 메모리를 operator new로 받고, 배치 new(placement new)로 객체를 생성하고, 재할당 때는 std::move_if_noexcept로 옮깁니다. 이동 생성자가 예외를 던질 수 있는 타입이면 복사로 대체해, 도중에 실패해도 원래 버퍼가 그대로 남는 강한 예외 보장을 지킵니다. 표준 vector가 이동 생성자에 noexcept를 붙이라고 요구하는 이유가 이것입니다.

링 버퍼: 고정 메모리로 흐르는 데이터 받기

UART 수신, 센서 샘플, 로그처럼 끝없이 흘러오는 데이터를 고정 크기 메모리로 받으려면 배열의 끝과 처음을 이어 붙인 원형 버퍼(링 버퍼)를 씁니다. 세 가지 기법이 실무 구현의 표준입니다.

  1. 용량을 2의 거듭제곱으로: i % N 대신 i & (N−1). 나눗셈이 사라집니다.
  2. 인덱스를 자유롭게 증가시키기: head와 tail을 감싸지 않고 계속 올리고, 쓸 때만 마스크합니다. 부호 없는 정수 뺄셈 head − tail이 오버플로를 넘어서도 항상 채워진 개수가 되므로, "가득 참"과 "비어 있음"을 칸 하나 버리지 않고 구분할 수 있습니다.
  3. 단일 생산자·단일 소비자(SPSC)면 락이 필요 없다: head는 생산자만, tail은 소비자만 씁니다. 데이터를 쓴 뒤 head를 release로 공개하고, 반대편은 acquire로 읽으면 순서가 보장됩니다.

연결 리스트, 스택, 큐

이 장을 마치면: 연결 리스트가 실제로 유리한 경우를 가려낼 수 있고, 커널 스타일 침투형(intrusive) 리스트를 구현하며, 네 언어에서 스택과 큐를 올바른 컨테이너로 표현할 수 있습니다.

연결 리스트가 이기는 경우는 생각보다 적다

교과서는 연결 리스트의 장점으로 "O(1) 삽입·삭제"를 꼽습니다. 단서가 붙습니다. 위치를 이미 알고 있을 때입니다. 위치를 찾는 데 O(n)이 걸리고, 그 탐색은 1장에서 본 것처럼 배열 탐색보다 몇 배에서 수십 배 느립니다. 그래서 "중간 삽입이 잦으니 리스트"라는 판단은 실측에서 자주 뒤집힙니다.

연결 리스트가 정말 이기는 경우는 다음과 같습니다.

  • 객체를 이미 손에 쥐고 있고, 그 객체를 O(1)에 빼거나 옮겨야 할 때 (LRU 캐시, 스케줄러 run queue, 타이머 취소)
  • 원소 주소가 절대 바뀌면 안 될 때 (다른 곳에서 포인터로 참조)
  • 리스트 두 개를 O(1)에 이어 붙이거나 잘라 옮길 때 (splice)
  • 메모리 할당을 할 수 없는 문맥에서 이미 존재하는 객체들을 엮을 때 (침투형 리스트)

unique_ptr 체인의 기본 소멸자는 노드마다 다음 노드의 소멸자를 부르는 재귀입니다. 노드 100만 개짜리 리스트를 지우면 스택 프레임 100만 개가 쌓여 스택 오버플로가 납니다. 소멸자에서 반복문으로 하나씩 끊어 내야 합니다. Rust의 Box 체인도 똑같은 문제가 있어 Drop을 직접 구현합니다.

커널은 리스트를 객체 안에 넣는다

일반적인 리스트는 노드가 값을 담습니다. 리눅스 커널의 list_head는 반대로 객체가 링크를 담습니다. 구조체 안에 prev/next 필드를 넣고, 링크 주소에서 container_of로 바깥 구조체 주소를 역산합니다.

  • 할당이 객체 하나로 끝납니다. 노드를 따로 만들지 않습니다.
  • 객체 하나가 링크 필드를 여러 개 가지면 여러 리스트에 동시에 들어갈 수 있습니다.
  • 헤드를 원형 이중 연결로 만들어 빈 리스트, 첫 노드, 마지막 노드의 특수 처리가 사라집니다.

스택과 큐는 자료구조라기보다 인터페이스다

스택(LIFO)은 함수 호출, 실행 취소, 괄호 짝 맞추기, 반복형 DFS(8장)에 쓰입니다. 큐(FIFO)는 작업 대기열, 메시지 버퍼, BFS(8장)에 쓰입니다. 둘 다 "어떤 순서로 꺼내는가"라는 약속이고, 구현은 배열이나 링 버퍼가 거의 항상 최선입니다.

흔한 함정

Python에서 list.pop(0)이나 list.insert(0, x)로 큐를 만들면 매번 전체 원소를 미는 O(n)입니다. 큐에는 반드시 deque를 쓰세요.

Rust에서 연결 리스트가 어려운 이유

Rust의 규칙은 "값의 소유자는 하나, 가변 참조는 동시에 하나"입니다. 단일 연결 리스트는 각 노드를 앞 노드가 소유하므로 Option<Box<Node>>로 자연스럽게 표현됩니다. 이중 연결 리스트는 노드 하나를 앞뒤 두 노드가 가리켜야 하므로 소유 규칙과 정면으로 부딪힙니다. 해법은 세 가지입니다.

  • Rc<RefCell<Node>> + Weak: 안전하지만 런타임 비용과 장황함이 큽니다.
  • unsafe 원시 포인터: 표준 LinkedList가 내부적으로 쓰는 방법. 불변식을 직접 증명해야 합니다.
  • 아레나 + 인덱스: 노드를 Vec에 넣고 포인터 대신 usize 인덱스로 연결. 안전하고, 캐시 친화적이고, 직렬화도 쉽습니다. 9장의 유니온-파인드와 11장의 트라이가 이 방식입니다.

Rust 커뮤니티의 고전 Learning Rust With Entirely Too Many Linked Lists는 이 주제만으로 책 한 권을 씁니다. 연결 리스트로 소유권을 익히고, 실무에서는 Vec과 VecDeque를 쓰라는 것이 결론입니다.
