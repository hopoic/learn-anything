Rust 지도와 첫 프로그램

이 장을 마치면: Rust가 어떤 종류의 버그를 컴파일 타임에 막고 어떤 것은 막지 않는지 구분할 수 있고, cargo로 프로젝트를 만들고 빌드·실행·검사하는 기본 흐름을 설명할 수 있으며, println! 포맷 문법으로 값을 출력할 수 있습니다.

Rust가 푸는 문제는 하나다: 안전과 제어를 함께 갖는 것

시스템 프로그래밍 언어는 오랫동안 두 진영 중 하나를 골라야 했습니다. C와 C++은 메모리 배치와 성능을 완전히 제어하게 해 주는 대신, 해제한 메모리 사용(use-after-free), 이중 해제, 버퍼 오버플로, 데이터 경쟁 같은 버그를 프로그래머가 스스로 막아야 합니다. Java나 Go 같은 언어는 가비지 컬렉터(GC)로 안전을 얻는 대신 런타임과 예측하기 어려운 정지 시간을 받아들입니다.

Rust는 세 번째 길을 택했습니다. 메모리를 언제 해제할지, 누가 무엇을 언제 바꿀 수 있는지를 타입 시스템의 규칙으로 표현하고, 컴파일러가 그 규칙을 컴파일 타임에 검사합니다. 규칙을 통과한 프로그램은 GC 없이도 메모리 오류와 데이터 경쟁이 없습니다. 이 책의 2–4장이 그 규칙(소유권과 빌림)이고, 나머지는 그 위에 쌓은 표현력입니다.

이것이 실무에서 왜 중요한지는 숫자가 말해 줍니다. Microsoft와 Chromium 팀은 각자 보안 취약점의 약 70%가 메모리 안전성 문제라고 보고했고, 리눅스 커널은 6.1(2022년 12월)부터 Rust로 드라이버를 쓸 수 있게 되었습니다. Android 팀은 새 코드를 메모리 안전 언어로 쓰면서 메모리 안전 취약점의 비율이 크게 줄었다고 발표했습니다. 임베디드 쪽에서도 no_std 환경과 embedded-hal 생태계가 자리를 잡았고, 안전 인증용 컴파일러(Ferrocene)도 나왔습니다.

무엇을 막고, 무엇은 막지 않는가

Rust를 처음 배울 때 가장 흔한 오해는 "Rust로 짜면 버그가 없다"입니다. 정확히는 정의되지 않은 동작(undefined behavior, UB)으로 이어지는 특정 버그 부류를 safe Rust에서 없앱니다. 논리 오류, 교착 상태(deadlock), 메모리 누수는 여전히 가능합니다. 또 어떤 검사는 컴파일 타임이 아니라 런타임에 일어나 panic으로 프로그램을 멈춥니다. 아래 벤치로 감을 잡아 두면 이후 장들이 어디를 향하는지 보입니다.

cargo: 빌드 도구이자 패키지 관리자

Rust 툴체인은 rustup으로 설치하고 관리합니다. rustup은 컴파일러(rustc), 빌드 도구(cargo), 표준 라이브러리, 린터(clippy), 포매터(rustfmt)를 버전별로 설치합니다. 실무에서 rustc를 직접 부르는 일은 거의 없고, 모든 것을 cargo로 합니다.

$ curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh # install rustup (Linux/macOS) $ cargo new hello && cd hello # creates Cargo.toml and src/main.rs $ cargo run # build (debug) and run $ cargo check # type-check only: the fastest feedback loop $ cargo build --release # optimized build in target/release/ $ cargo clippy # lints: hundreds of "this works, but..." hints $ cargo fmt # format the whole project $ cargo test # build and run unit/integration/doc tests [package] name = "hello" version = "0.1.0" edition = "2024" # language edition: opt-in, per crate [dependencies] # serde = { version = "1", features = ["derive"] } # crates come from crates.io

edition은 Rust가 하위 호환을 깨지 않고 문법을 다듬는 장치입니다. 에디션은 크레이트(컴파일 단위)마다 따로 고르고, 서로 다른 에디션의 크레이트끼리 문제없이 링크됩니다. 2015, 2018, 2021에 이어 2024 에디션이 Rust 1.85(2025년 2월)와 함께 안정화되었고, 이 책은 2024 에디션을 기준으로 합니다.

시스템 엔지니어의 눈으로

cargo는 make + CMake + pkg-config + 패키지 저장소를 한 도구로 합친 것에 가깝습니다. 크로스 컴파일도 rustup target add aarch64-unknown-linux-gnu로 타깃 표준 라이브러리를 받고 링커만 지정하면 됩니다. Jetson 같은 aarch64 보드용 빌드는 16장에서 다룹니다.

첫 프로그램: println!은 함수가 아니라 매크로다

첫 예제를 실행해 보세요. 이름 뒤의 !는 매크로 호출이라는 표시입니다. println!은 컴파일 타임에 포맷 문자열을 해석해서, 인자 개수나 타입이 맞지 않으면 컴파일 오류를 냅니다. C의 printf("%d", "oops") 같은 실수가 원천적으로 막힙니다.

fn main() { let robot = "AMR-07"; let battery = 87.456_f64; // underscores are allowed in number literals let wheels = [0.31, 0.29, 0.30, 0.30]; println!("Hello, {robot}!"); // inline named argument println!("battery = {:.1}%", battery); // precision println!("battery = {battery:>8.2}|"); // width 8, right-aligned println!("wheels = {:?}", wheels); // {:?} = Debug formatting println!("hex = {:#06x}, bin = {:#010b}", 255, 5); eprintln!("this line goes to stderr"); }

포맷 지정자 중 {}는 사람이 읽는 표시(Display 트레잇), {:?}는 개발자용 디버그 표시(Debug 트레잇)를 씁니다. 배열은 Display가 없어 {:?}로만 출력됩니다. 트레잇은 8장에서 자세히 다룹니다. 지금은 "타입이 어떤 기능을 구현했는지에 따라 쓸 수 있는 포맷이 정해진다"고만 기억하세요.

이번에는 일부러 틀린 코드를 실행해 봅시다. Rust 오류 메시지는 오류 코드(E0277 같은), 문제 위치, 그리고 대개 고치는 방법까지 알려 줍니다. 오류 코드는 rustc --explain E0277로 자세한 설명을 볼 수 있습니다.

fn main() { let wheels = [0.31, 0.29]; println!("wheels = {}", wheels); // arrays do not implement Display println!("{} and {}", 1); // too few arguments }
핵심 정리
  • Rust는 메모리 오류와 데이터 경쟁을 컴파일 타임 규칙으로 막습니다. GC가 없으니 런타임 비용도 C와 비슷합니다.
  • 배열 범위 초과 같은 일부 검사는 런타임 panic이고, 논리 오류·교착·누수는 막지 않습니다.
  • 개발은 cargo check → cargo clippy → cargo test 순환이 기본입니다.

다음 장에서는 변수, 기본 타입, 제어 흐름을 C와 비교하며 빠르게 훑습니다. 겉보기엔 비슷하지만 "모든 것이 식(expression)"이라는 점과 정수 오버플로 처리 방식이 다릅니다.
