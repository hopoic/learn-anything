두려움 없는 동시성

이 장을 마치면: Send와 Sync가 무엇을 보장하는지 설명하고 주요 타입의 Send/Sync 여부를 판별할 수 있으며, thread::scope, Arc<Mutex<T>>, 채널, 원자 타입 중 문제에 맞는 공유 방식을 고를 수 있고, Rust가 막아 주는 것(데이터 경쟁)과 막지 못하는 것(교착, 경쟁 조건)을 구분할 수 있습니다.

11장의 Rc와 RefCell은 단일 스레드 전용이었습니다. 이 장에서는 그 제약이 어디서 오는지, 그리고 스레드 사이에서 같은 일을 하려면 무엇을 써야 하는지 봅니다. 핵심은 새 규칙이 아니라 4장의 "공유 XOR 변경" 규칙이 스레드에도 그대로 적용된다는 것입니다.

Send와 Sync: 두 개의 마커 트레잇이 전부다

  • T: Send — T 값의 소유권을 다른 스레드로 옮겨도 안전하다.
  • T: Sync — &T를 여러 스레드가 동시에 가져도 안전하다. (정의상 T: Sync ⇔ &T: Send)

둘 다 메서드가 없는 마커 트레잇이고, 구성 요소가 모두 Send/Sync이면 컴파일러가 자동으로 구현합니다. 그리고 thread::spawn은 넘겨받는 클로저에 F: Send + 'static을 요구합니다. 이 두 줄의 조합으로 데이터 경쟁이 컴파일 오류가 됩니다. Rc는 카운트를 비원자적으로 바꾸므로 Send가 아니고, 따라서 Rc를 품은 클로저는 다른 스레드로 보낼 수 없습니다.

use std::rc::Rc; use std::thread; fn main() { let shared = Rc::new(vec![1, 2, 3]); let s2 = Rc::clone(&shared); let h = thread::spawn(move || { // error[E0277]: `Rc>` cannot be sent between threads safely println!("{:?}", s2); }); h.join().unwrap(); }

scoped thread: 스택 데이터를 그대로 빌려주기

thread::spawn이 'static을 요구하는 이유는 새 스레드가 언제 끝날지 모르기 때문입니다. 지역 변수를 빌려주면 함수가 먼저 반환해 매달린 참조가 될 수 있습니다. thread::scope는 "이 블록이 끝나기 전에 안의 모든 스레드를 join한다"고 보장하므로, 지역 데이터를 그냥 빌려줄 수 있습니다. 데이터를 나눠 병렬 처리하는 대부분의 경우에 가장 먼저 고려할 도구입니다.

use std::thread; fn main() { let scan: Vec = (0..1_000).map(|i| ((i * 37) % 1000) as f32 / 100.0).collect(); let mut mins = [0.0f32; 4]; thread::scope(|s| { // Split the data into 4 chunks and the output into 4 disjoint &mut slots. for (chunk, slot) in scan.chunks(250).zip(mins.iter_mut()) { s.spawn(move || { *slot = chunk.iter().copied().fold(f32::INFINITY, f32::min); }); } }); // all threads are joined here; borrows of `scan` and `mins` end println!("per-chunk minimum = {mins:?}"); println!("global minimum = {}", mins.iter().copied().fold(f32::INFINITY, f32::min)); }

mins.iter_mut()가 원소마다 겹치지 않는 &mut를 하나씩 만들어 주므로, 네 스레드가 각자 자기 칸만 씁니다. 같은 칸을 두 스레드에 주려고 하면 4장의 규칙대로 컴파일되지 않습니다. 락이 하나도 없는데 데이터 경쟁도 없습니다.

공유 상태: Arc + Mutex, 그리고 원자 타입

스레드들이 같은 값을 계속 함께 바꿔야 하면 단일 스레드의 Rc<RefCell<T>>에 대응하는 Arc<Mutex<T>>를 씁니다. Rust의 Mutex는 C의 pthread mutex와 결정적으로 다릅니다. 보호하는 데이터를 안에 품고 있어서, 락을 잡지 않으면 데이터에 접근할 방법이 없습니다. lock()이 돌려주는 MutexGuard가 drop될 때 자동으로 풀립니다(RAII). 정수 카운터나 플래그처럼 단순한 값은 Atomic* 타입이 더 가볍습니다.

use std::collections::HashMap; use std::sync::atomic::{AtomicBool, AtomicU64, Ordering}; use std::sync::{Arc, Mutex, RwLock}; use std::thread; use std::time::Duration; fn main() { let latest: Arc>> = Arc::new(Mutex::new(HashMap::new())); let params = Arc::new(RwLock::new(0.5_f64)); // many readers, rare writers let frames = Arc::new(AtomicU64::new(0)); let running = Arc::new(AtomicBool::new(true)); let mut handles = Vec::new(); for (topic, base) in [("imu", 1.0), ("lidar", 10.0), ("odom", 100.0)] { let (latest, params, frames, running) = (latest.clone(), params.clone(), frames.clone(), running.clone()); handles.push(thread::spawn(move || { let mut i = 0.0; while running.load(Ordering::Relaxed) { let gain = *params.read().unwrap(); // read lock, released at end of statement { let mut map = latest.lock().unwrap(); // the ONLY way to reach the map map.insert(topic, base + i * gain); } // guard dropped: unlocked frames.fetch_add(1, Ordering::Relaxed); i += 1.0; thread::sleep(Duration::from_millis(2)); } })); } thread::sleep(Duration::from_millis(30)); *params.write().unwrap() = 2.0; // exclusive write lock thread::sleep(Duration::from_millis(30)); running.store(false, Ordering::Relaxed); for h in handles { h.join().unwrap(); } let map = latest.lock().unwrap(); let mut keys: Vec<_> = map.keys().collect(); keys.sort(); println!("topics = {keys:?}"); println!("frames > 30? {}", frames.load(Ordering::Relaxed) > 30); println!("Arc strong count now = {}", Arc::strong_count(&latest)); }
Ordering 한 줄 요약

Relaxed는 "이 변수 하나의 원자성"만 보장합니다. 카운터, 통계, 단순 중지 플래그에 충분합니다. 한 스레드가 데이터를 준비한 뒤 플래그로 "준비됐다"고 알리는 경우처럼 다른 메모리의 가시성까지 맞춰야 하면, 쓰는 쪽 Release + 읽는 쪽 Acquire를 짝지어 씁니다. 확신이 없으면 SeqCst로 시작하고, 원자 타입보다 Mutex나 채널을 먼저 고려하세요. 더 깊은 내용은 부록 B의 Rust Atomics and Locks가 표준 참고서입니다.

메시지 전달: 공유하지 말고 보내라

공유 상태보다 더 단순한 설계는 소유권을 메시지로 넘기는 것입니다. std::sync::mpsc 채널(다수 생산자, 단일 소비자)로 값을 보내면 소유권이 수신 스레드로 이동하므로, 보낸 쪽은 더 이상 그 값을 건드릴 수 없습니다. 3장의 이동 규칙이 그대로 스레드 안전성이 됩니다. 모든 송신자(Sender)가 drop되면 수신 루프가 자연스럽게 끝납니다.

use std::sync::mpsc; use std::thread; use std::time::Duration; #[derive(Debug)] enum Msg { Scan { id: u32, ranges: Vec }, Status(&'static str) } fn main() { let (tx, rx) = mpsc::sync_channel::(4); // bounded: back-pressure when full let lidar_tx = tx.clone(); let lidar = thread::spawn(move || { for id in 0..3 { let ranges = vec![1.0 + id as f32; 360]; // allocated here... lidar_tx.send(Msg::Scan { id, ranges }).unwrap(); // ...ownership moves to the receiver thread::sleep(Duration::from_millis(5)); } }); let health = thread::spawn(move || { tx.send(Msg::Status("battery ok")).unwrap(); }); // original tx moved in and dropped here for msg in rx { // ends when every Sender is dropped match msg { Msg::Scan { id, ranges } => println!("scan {id}: {} beams, first {}", ranges.len(), ranges[0]), Msg::Status(s) => println!("status: {s}"), } } lidar.join().unwrap(); health.join().unwrap(); println!("all senders gone, receiver loop finished"); }
Rust가 막아 주지 않는 것
  • 교착 상태: 두 스레드가 락 A, B를 반대 순서로 잡으면 여전히 멈춥니다. 락 순서를 정하고, 락을 잡은 채 다른 락이나 채널 수신을 기다리지 마세요.
  • 경쟁 조건(race condition): "확인하고 나서 행동하기"를 두 번의 락으로 나누면 그 사이에 상태가 바뀝니다. 데이터 경쟁(data race, UB)과 달리 논리 버그이므로 컴파일러가 모릅니다.
  • 독약 처리(poisoning): 락을 잡은 스레드가 panic하면 Mutex가 poisoned 상태가 되어 lock()이 Err를 돌려줍니다. 예제의 unwrap()은 "그러면 우리도 멈춘다"는 선택입니다.
ROS 2 엔지니어의 눈으로

콜백 그룹과 executor로 스레드를 나누는 ROS 2에서 가장 흔한 버그는 콜백 사이의 공유 상태 경쟁입니다. Rust 바인딩(rclrs, r2r)에서는 콜백 클로저가 Send를 요구받기 때문에, 공유 상태를 Arc<Mutex<_>>로 감싸지 않으면 아예 컴파일되지 않습니다. 경쟁을 리뷰가 아니라 타입이 막는 것입니다.

스레드는 수천 개 단위의 동시 작업에는 무겁습니다. 네트워크 연결 수만 개를 한 스레드에서 다루는 방법, async/await가 다음 장의 주제입니다.
