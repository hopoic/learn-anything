스마트 포인터와 내부 가변성

이 장을 마치면: Box, Rc/Arc, Weak, Cell, RefCell이 각각 소유권 규칙의 어떤 부분을 바꾸는지 설명할 수 있고, Rc<RefCell<T>> 패턴과 그 런타임 비용(panic 가능성)을 이해하며, Weak로 순환 참조 누수를 끊을 수 있습니다.

지금까지의 규칙은 "소유자는 하나, 변경은 배타적"이었습니다. 대부분의 코드는 이 규칙 안에서 깔끔하게 짜입니다. 하지만 그래프, 트리의 부모 링크, 여러 곳에서 공유하는 캐시처럼 규칙에 딱 맞지 않는 구조도 있습니다. 스마트 포인터는 규칙을 버리는 것이 아니라, 검사를 컴파일 타임에서 런타임으로 옮기는 도구입니다.

Box: 힙에 두기, 재귀 타입, 트레잇 객체

Box<T>는 가장 단순한 스마트 포인터입니다. 값을 힙에 두고 포인터 하나만 들고 있으며, Box가 drop되면 힙 값도 drop됩니다. 크기를 컴파일 타임에 알 수 없는 것(재귀 타입, dyn Trait)을 담을 때 필요합니다. 연결 리스트나 식 트리의 노드가 자기 타입을 직접 품으면 크기가 무한이 되므로, Box로 한 번 감쌉니다.

// An expression tree for a tiny "mission script": recursive, so children are boxed. #[derive(Debug)] enum Expr { Num(f64), Var(&'static str), Add(Box, Box), Mul(Box, Box), } use Expr::*; fn eval(e: &Expr, speed: f64) -> f64 { match e { Num(n) => *n, Var("speed") => speed, Var(other) => panic!("unknown variable {other}"), Add(a, b) => eval(a, speed) + eval(b, speed), // &Box auto-derefs to &Expr Mul(a, b) => eval(a, speed) * eval(b, speed), } } fn main() { // distance = speed * 2.5 + 0.3 let dist = Add(Box::new(Mul(Box::new(Var("speed")), Box::new(Num(2.5)))), Box::new(Num(0.3))); println!("{dist:?}"); println!("distance at 0.8 m/s = {:.2} m", eval(&dist, 0.8)); println!("size_of::() = {} bytes", std::mem::size_of::()); }

Rc + RefCell: 공유 소유와 런타임 빌림 검사

Rc<T>를 clone()하면 값이 복제되지 않고 참조 카운트만 1 늘어납니다. 마지막 Rc가 drop될 때 값이 해제됩니다. 단, Rc는 내용에 대해 &T만 줍니다. 여러 소유자가 동시에 &mut를 가지면 4장의 규칙이 깨지기 때문입니다. 공유하면서 바꾸고 싶다면 RefCell을 넣어 Rc<RefCell<T>>로 만듭니다. RefCell은 borrow()/borrow_mut()를 부를 때마다 4장의 규칙을 런타임에 검사하고, 위반하면 panic합니다.

use std::cell::RefCell; use std::rc::Rc; #[derive(Debug)] struct Map { obstacles: Vec<(i32, i32)> } struct Planner { map: Rc> } struct Perception { map: Rc> } impl Perception { fn detect(&self, p: (i32, i32)) { self.map.borrow_mut().obstacles.push(p); } } impl Planner { fn blocked(&self, p: (i32, i32)) -> bool { self.map.borrow().obstacles.contains(&p) } } fn main() { let map = Rc::new(RefCell::new(Map { obstacles: vec![] })); let perception = Perception { map: Rc::clone(&map) }; // Rc::clone: count += 1, no deep copy let planner = Planner { map: Rc::clone(&map) }; println!("strong_count = {}", Rc::strong_count(&map)); perception.detect((3, 4)); println!("blocked (3,4)? {}", planner.blocked((3, 4))); println!("map = {:?}", map.borrow()); // The borrow rules still apply, just at run time: let reader = map.borrow(); // shared borrow alive... println!("try_borrow_mut while reading: {:?}", map.try_borrow_mut().map(|_| ())); perception.detect((5, 5)); // ...so this borrow_mut() panics println!("unreachable {}", reader.obstacles.len()); }

마지막 부분이 이 패턴의 대가입니다. 컴파일러가 잡아 주던 오류가 런타임 panic(already borrowed: BorrowMutError)으로 바뀝니다. 그래서 RefCell은 "빌림 기간이 짧고 구조상 겹치지 않는다"는 것을 사람이 확신할 때만 쓰고, 확실하지 않으면 try_borrow_mut로 실패를 다루세요.

Weak로 순환을 끊는다

참조 카운트의 고전적 약점은 순환입니다. 부모가 자식을, 자식이 부모를 Rc로 가리키면 둘 다 카운트가 0이 되지 않아 영원히 해제되지 않습니다. Rust에서 메모리 누수는 "안전한" 동작이라 컴파일러가 막지 않습니다(1장 벤치). 해법은 한쪽 방향을 Weak로 만드는 것입니다. Weak는 카운트를 올리지 않고, 쓸 때마다 upgrade()로 값이 아직 살아 있는지 확인해 Option<Rc<T>>를 받습니다.

실습 벤치 11-A · Rc와 Weak의 카운트STEPPER · 8 STEPS

use std::cell::RefCell; use std::rc::{Rc, Weak}; #[derive(Debug)] struct Frame { name: String, parent: RefCell>, // child -> parent: does NOT own children: RefCell>>, // parent -> children: owns } impl Frame { fn new(name: &str) -> Rc { Rc::new(Frame { name: name.into(), parent: RefCell::new(Weak::new()), children: RefCell::new(vec![]) }) } fn attach(parent: &Rc, child: Rc) { *child.parent.borrow_mut() = Rc::downgrade(parent); parent.children.borrow_mut().push(child); } fn path(&self) -> String { match self.parent.borrow().upgrade() { Some(p) => format!("{}/{}", p.path(), self.name), None => self.name.clone(), } } } impl Drop for Frame { fn drop(&mut self) { println!(" drop frame {}", self.name); } } fn main() { let lidar = Frame::new("lidar"); { let base = Frame::new("base_link"); let mast = Frame::new("mast"); Frame::attach(&base, mast.clone()); Frame::attach(&mast, lidar.clone()); println!("path = {}", lidar.path()); println!("base: strong={} weak={}", Rc::strong_count(&base), Rc::weak_count(&base)); println!("mast: strong={} weak={}", Rc::strong_count(&mast), Rc::weak_count(&mast)); println!("leaving scope: base and mast lose their outside owners"); } println!("after scope, lidar.path() = {} (parent gone, upgrade() returned None)", lidar.path()); }
C++ 개발자의 눈으로

Box ≈ unique_ptr, Arc ≈ shared_ptr, Weak ≈ weak_ptr입니다. 차이는 두 가지입니다. Rust에는 단일 스레드용 Rc가 따로 있어 원자 연산 비용을 피할 수 있고(실수로 스레드 간에 넘기면 컴파일 오류, 12장), shared_ptr<T>와 달리 Rc<T>는 내용을 바꿀 수 없어서 공유 + 변경이 필요하면 RefCell을 명시해야 합니다. 비용이 드는 선택이 타입에 드러나는 셈입니다.

흔한 함정
  • Rc<RefCell<T>>를 기본 설계로 쓰면 다른 언어의 객체 그래프를 흉내 내게 되고, 빌림 오류가 런타임 panic으로 바뀝니다. 먼저 소유 트리 + 인덱스(Vec + usize ID) 구조를 검토하세요. 그래프에는 아레나(arena) 패턴이 더 Rust답습니다.
  • borrow()로 얻은 Ref를 오래 들고 있지 마세요. 함수 호출을 건너 살아 있으면 다른 곳의 borrow_mut()가 panic합니다.
