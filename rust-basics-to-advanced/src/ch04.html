빌림과 슬라이스

이 장을 마치면: 공유 참조(&T)와 가변 참조(&mut T)의 규칙을 "공유 XOR 변경"으로 설명할 수 있고, 빌림 검사기 오류(E0499, E0502, E0505, E0106)를 보고 원인을 짚어 고칠 수 있으며, &str과 &[T] 슬라이스를 매개변수로 쓰는 API를 설계할 수 있습니다.

3장에서 값을 넘기면 소유권이 넘어간다고 했습니다. 빌림은 소유권은 그대로 두고 잠시 접근 권한만 빌려주는 것입니다.

규칙은 하나: 공유하거나, 변경하거나

참조에는 두 종류가 있습니다.

참조할 수 있는 것동시에 몇 개
&T 공유 참조읽기여러 개 가능
&mut T 가변(배타) 참조읽기 + 쓰기단 하나, 그동안 다른 참조 없음

즉 어떤 값에 대해 "여러 명이 읽기" 또는 "한 명이 쓰기" 중 하나만 허용됩니다(aliasing XOR mutability). 그리고 참조는 원래 값보다 오래 살 수 없습니다. 이 두 문장이 빌림 검사기(borrow checker)가 확인하는 전부입니다. 단순하지만, 이것만으로 반복자 무효화, 해제 후 사용, 데이터 경쟁이 한꺼번에 사라집니다.

fn total(ranges: &Vec) -> f32 { // borrow: read-only access ranges.iter().sum() } fn clip(ranges: &mut Vec, max: f32) { // mutable borrow: exclusive access for r in ranges.iter_mut() { if *r > max { *r = max; } // *r: write through the reference } } fn main() { let mut scan = vec![1.2, 30.0, 0.8, 12.5]; let a = &scan; // any number of shared borrows... let b = &scan; println!("sum = {}, len = {}", total(a), b.len()); // a and b are not used after this line, so their borrows end here (NLL) clip(&mut scan, 10.0); // ...or one mutable borrow println!("clipped = {scan:?}"); // the owner is still `scan` }

주석의 NLL(non-lexical lifetimes)이 중요합니다. 빌림은 변수의 스코프 끝까지가 아니라 마지막으로 사용된 지점까지만 유효합니다. 그래서 위 코드에서 a, b가 아직 스코프 안에 있는데도 &mut scan이 허용됩니다.

빌림 검사기가 막아 주는 진짜 버그

대표적인 오류를 직접 보겠습니다. 벡터의 원소를 참조로 들고 있는 동안 push를 하면 컴파일되지 않습니다. 처음에는 과잉 규제처럼 보이지만, push가 용량을 넘겨 버퍼를 재할당하면 그 참조는 해제된 메모리를 가리키게 됩니다. C++에서 std::vector 반복자 무효화로 알려진 바로 그 버그입니다.

fn main() { let mut waypoints = vec![(0.0, 0.0), (1.0, 2.0)]; let first = &waypoints[0]; // shared borrow of an element... waypoints.push((3.0, 4.0)); // error[E0502]: mutable borrow while shared borrow is alive println!("first = {first:?}"); // ...which is still used here } // The same program in C++ compiles, then reads freed memory if push_back reallocates. std::vector> waypoints{{0, 0}, {1, 2}}; const auto& first = waypoints[0]; waypoints.push_back({3, 4}); // may reallocate: `first` now dangles std::printf("%f\n", first.first); // undefined behavior

고치는 방법은 대개 셋 중 하나입니다. (1) 참조를 쓰는 일을 변경 전에 끝낸다, (2) 참조 대신 값을 복사해 둔다(let first = waypoints[0]; — 튜플이 Copy라서 가능), (3) 인덱스를 들고 있다가 필요할 때 다시 접근한다. 오류 예제를 편집해서 세 가지를 모두 시도해 보세요.

참조가 원래 값보다 오래 살려는 경우도 막습니다. 함수가 지역 변수의 참조를 반환하려 하면 컴파일러는 "빌려 온 값이 어디서 왔는지 알 수 없다"(E0106)고 거부합니다. 해법은 소유한 값을 반환하는 것입니다.

fn make_label() -> &str { // error[E0106]: missing lifetime specifier let s = String::from("front-lidar"); &s // s is dropped at the end of this function } fn main() { println!("{}", make_label()); }

슬라이스: 포인터 + 길이를 한 타입으로

슬라이스는 연속된 메모리의 일부를 빌리는 참조입니다. &[T]는 배열·벡터의 일부, &str은 UTF-8 문자열의 일부입니다. 내부적으로는 (포인터, 길이) 두 워드로 된 "팻 포인터"(fat pointer)라서, C에서 늘 따로 넘기던 buf와 len이 한 값이 되고, 범위를 벗어난 접근은 검사됩니다.

// Take &[u8] / &str, not &Vec / &String: callers can pass arrays, vectors, or sub-ranges. fn checksum(frame: &[u8]) -> u8 { frame.iter().fold(0u8, |acc, b| acc ^ b) } fn first_word(s: &str) -> &str { match s.find(' ') { Some(i) => &s[..i], None => s, } } fn main() { let packet: Vec = vec![0xA5, 0x01, 0x04, 0x10, 0x20, 0x30, 0x40]; let header = &packet[..3]; // &[u8], len 3 let payload = &packet[3..]; // &[u8], len 4 println!("header {header:02X?} payload {payload:02X?} xor {:#04X}", checksum(payload)); let fixed: [u8; 4] = [1, 2, 3, 4]; println!("array xor = {}", checksum(&fixed)); // &[u8; 4] coerces to &[u8] let cmd = String::from("MOVE 1.5 0.0"); let verb = first_word(&cmd); // &String coerces to &str println!("verb = {verb}, literal = {}", first_word("STOP now")); println!("size of &[u8] = {} bytes, size of &u8 = {} bytes", std::mem::size_of::<&[u8]>(), std::mem::size_of::<&u8>()); let (left, right) = packet.split_at(2); // two non-overlapping borrows println!("{left:?} | {right:?}"); }
C 개발자의 눈으로

&T는 "널이 될 수 없고, 정렬되어 있고, 가리키는 값이 살아 있다는 것이 증명된" 포인터입니다. &mut T는 거기에 더해 restrict가 컴파일러에 의해 검증된 포인터입니다. 그래서 Rust 컴파일러는 C에서 restrict를 붙여야 얻는 최적화를 기본으로 얻습니다.

흔한 함정
  • 매개변수를 &String이나 &Vec<T>로 받지 마세요. &str, &[T]가 더 일반적이고 비용은 같습니다. clippy도 이를 경고합니다(ptr_arg).
  • 문자열 슬라이스 인덱스는 바이트 위치입니다. 한글처럼 여러 바이트로 된 문자의 중간을 자르면 panic합니다(7장).
  • "빌림 검사기와 싸운다"고 느껴지면 대개 데이터 구조가 소유 관계를 흐리고 있다는 신호입니다. 누가 무엇을 소유하는지부터 다시 그려 보세요.
