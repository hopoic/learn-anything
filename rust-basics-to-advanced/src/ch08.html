제네릭과 트레잇

이 장을 마치면: 트레잇을 정의·구현하고 트레잇 경계(T: Trait, where)로 제네릭 함수를 제약할 수 있고, 제네릭(정적 디스패치, 단형화)과 dyn Trait(동적 디스패치, vtable)의 비용과 쓰임새를 비교해 고를 수 있으며, derive·연산자 오버로딩·고아 규칙(orphan rule)을 설명할 수 있습니다.

7장까지 쓴 Vec<T>와 Option<T>는 모두 제네릭입니다. 이 장에서는 그 T에 "어떤 능력이 있어야 하는가"를 표현하는 트레잇을 배웁니다. 트레잇은 Rust에서 인터페이스, 연산자, 형변환, 스레드 안전성까지 거의 모든 추상화의 기반입니다.

트레잇은 "이 타입이 할 수 있는 일"의 계약이다

트레잇은 메서드 시그니처의 묶음입니다. 기본 구현을 줄 수 있고, 어떤 타입이든 impl Trait for Type으로 구현할 수 있습니다. 상속은 없습니다. 대신 여러 트레잇을 조합합니다.

trait Sensor { fn name(&self) -> String; fn read(&mut self) -> f64; fn read_avg(&mut self, n: u32) -> f64 { // default method: uses the required ones (0..n).map(|_| self.read()).sum::() / n as f64 } } struct Thermistor { raw: u16 } struct Ultrasonic { echo_us: u32, tick: u32 } impl Sensor for Thermistor { fn name(&self) -> String { "thermistor".into() } fn read(&mut self) -> f64 { self.raw = self.raw.wrapping_add(3); 25.0 + (self.raw % 10) as f64 * 0.1 } } impl Sensor for Ultrasonic { fn name(&self) -> String { format!("ultrasonic#{}", self.tick) } fn read(&mut self) -> f64 { self.tick += 1; self.echo_us as f64 * 0.0343 / 2.0 // cm } fn read_avg(&mut self, _n: u32) -> f64 { self.read() } // override the default } // Generic function with a trait bound: one copy is compiled per concrete type. fn report(s: &mut S) { println!("{:<14} avg = {:.2}", s.name(), s.read_avg(4)); } // Same thing, `impl Trait` in argument position (sugar for a generic). fn report_twice(s: &mut impl Sensor) { report(s); report(s); } fn main() { let mut t = Thermistor { raw: 0 }; let mut u = Ultrasonic { echo_us: 580, tick: 0 }; report(&mut t); report_twice(&mut u); }

derive와 표준 트레잇: 공짜로 얻는 능력

자주 쓰는 표준 트레잇은 #[derive(...)]로 자동 구현됩니다. 어떤 트레잇을 구현했는지가 그 타입으로 할 수 있는 일을 결정합니다. ==는 PartialEq, {:?}는 Debug, HashMap 키가 되려면 Eq + Hash, 정렬하려면 Ord가 필요합니다. + 같은 연산자도 std::ops::Add 트레잇을 구현하면 됩니다.

use std::collections::HashSet; use std::fmt; use std::ops::{Add, Mul}; #[derive(Debug, Clone, Copy, PartialEq, Default)] struct Vec2 { x: f64, y: f64 } impl Add for Vec2 { type Output = Vec2; // associated type fn add(self, o: Vec2) -> Vec2 { Vec2 { x: self.x + o.x, y: self.y + o.y } } } impl Mul for Vec2 { type Output = Vec2; fn mul(self, k: f64) -> Vec2 { Vec2 { x: self.x * k, y: self.y * k } } } impl fmt::Display for Vec2 { fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result { write!(f, "({:.2}, {:.2})", self.x, self.y) } } #[derive(Debug, Clone, Copy, PartialEq, Eq, Hash, PartialOrd, Ord)] enum Priority { Low, Normal, High, Critical } // derive Ord: declaration order // A generic function bounded by several traits, written with `where`. fn largest(items: &[T]) -> Option<&T> where T: PartialOrd, { let mut best = items.first()?; for it in items { if it > best { best = it; } } Some(best) } fn main() { let p = Vec2 { x: 1.0, y: 2.0 } + Vec2 { x: 0.5, y: -1.0 } * 2.0; println!("p = {p} default = {:?}", Vec2::default()); let mut queue = vec![Priority::Normal, Priority::Critical, Priority::Low, Priority::High]; queue.sort(); println!("sorted = {queue:?}, max = {:?}", largest(&queue)); println!("largest f64 = {:?}", largest(&[0.3, 9.1, 2.2])); let unique: HashSet = [Priority::Low, Priority::Low, Priority::High].into_iter().collect(); println!("unique count = {}", unique.len()); }
고아 규칙(orphan rule)

impl Trait for Type은 트레잇이나 타입 중 적어도 하나가 내 크레이트 것일 때만 쓸 수 있습니다. 그래서 남의 타입 Vec<u8>에 남의 트레잇 Display를 구현할 수 없습니다. 두 크레이트가 같은 구현을 따로 넣어 충돌하는 일을 막기 위한 규칙입니다. 필요하면 15장의 newtype(struct Hex(Vec<u8>))으로 감싸서 구현합니다.

정적 디스패치 vs 동적 디스패치

여러 종류의 센서를 한 벡터에 담고 싶다면? 제네릭 Vec<T>는 한 가지 타입만 담습니다. 서로 다른 타입을 섞으려면 트레잇 객체 dyn Sensor를 씁니다. 크기를 모르는 타입이라 항상 포인터 뒤에 둡니다(Box<dyn Sensor>, &dyn Sensor).

trait Actuator { fn name(&self) -> &str; fn command(&mut self, value: f64) -> String; } struct Motor { id: u8, rpm: f64 } struct Gripper { closed: bool } impl Actuator for Motor { fn name(&self) -> &str { "motor" } fn command(&mut self, v: f64) -> String { self.rpm = v * 3000.0; format!("motor{} -> {} rpm", self.id, self.rpm) } } impl Actuator for Gripper { fn name(&self) -> &str { "gripper" } fn command(&mut self, v: f64) -> String { self.closed = v > 0.5; format!("gripper closed = {}", self.closed) } } fn main() { // A heterogeneous collection: each Box is (data ptr, vtable ptr). let mut outputs: Vec> = vec![ Box::new(Motor { id: 1, rpm: 0.0 }), Box::new(Gripper { closed: false }), Box::new(Motor { id: 2, rpm: 0.0 }), ]; for (i, a) in outputs.iter_mut().enumerate() { let out = a.command(0.2 * (i as f64 + 1.0)); // finish the &mut call first... println!("{:<8} {out}", a.name()); // ...then borrow again for name() } use std::mem::size_of; println!("Box = {} B, Box = {} B, &dyn Actuator = {} B", size_of::>(), size_of::>(), size_of::<&dyn Actuator>()); }

모든 트레잇이 dyn으로 쓰일 수 있는 것은 아닙니다. vtable에 담을 수 없는 메서드, 예컨대 제네릭 메서드나 Self를 값으로 반환하는 메서드가 있으면 그 트레잇은 "dyn 호환"(예전 용어로 object safe)이 아닙니다. 제네릭 메서드는 타입마다 다른 기계어가 필요한데 vtable에는 칸이 하나뿐이기 때문입니다.

C/C++ 개발자의 눈으로

dyn Trait는 C의 "ops 구조체(함수 포인터 테이블) + void *"를 언어가 만들어 주는 것이고, C++의 가상 함수와 달리 vtable 포인터가 객체 안이 아니라 참조 쪽에 붙습니다. 그래서 같은 Motor 값을 제네릭으로도, dyn으로도 쓸 수 있고, 트레잇을 쓰지 않는 값에는 vtable 비용이 전혀 없습니다. 제네릭은 C++ 템플릿처럼 단형화되지만, 경계(S: Sensor)를 선언 시점에 검사하므로 C++20 컨셉트처럼 오류가 짧고 정확합니다.

흔한 함정
  • "Java처럼" 모든 것을 Box<dyn Trait>로 설계하지 마세요. 기본은 제네릭이고, 런타임에 종류가 정해지거나 코드 크기가 문제일 때 dyn을 씁니다. 종류가 닫혀 있으면(정해진 몇 개) 열거형이 둘 다보다 나을 때가 많습니다.
  • 제네릭을 깊게 중첩하면 컴파일 시간과 바이너리 크기가 커집니다. 임베디드에서는 cargo bloat로 단형화 비용을 확인하세요.
