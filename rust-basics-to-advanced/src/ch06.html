오류 처리: Result와 ?

이 장을 마치면: 복구 가능한 오류(Result)와 복구 불가능한 오류(panic!)를 구분해 쓸 수 있고, ? 연산자가 무엇으로 펼쳐지는지 설명할 수 있으며, 라이브러리용 오류 열거형과 From 변환을 직접 설계할 수 있습니다.

5장의 Option은 "값이 없을 수 있음"을 표현했습니다. 이 장의 Result는 "실패할 수 있고, 실패하면 그 이유가 이것"을 표현합니다.

오류도 그냥 값이다

Rust에는 예외가 없습니다. 실패할 수 있는 함수는 Result<T, E>를 반환합니다. 정의는 enum Result<T, E> { Ok(T), Err(E) } 한 줄입니다. C의 "-1 반환 + errno"와 비슷하지만, 성공 값과 오류 값이 한 타입에 묶여 있어 오류를 확인하지 않고 성공 값을 꺼낼 방법이 없습니다. Result를 그냥 버리면 컴파일러가 unused_must_use 경고를 냅니다.

반대로 panic!은 "이 프로그램은 버그 상태다, 더 진행하면 안 된다"는 선언입니다. 기본 동작은 스택을 되감으며(unwind) 지역 값들을 drop하고 스레드를 끝내는 것이고, panic = "abort"로 설정하면 즉시 중단합니다. 펌웨어에서는 보통 abort를 씁니다.

버그panic!, assert!, unreachable! — 계약 위반, 불변식 파괴. 복구가 아니라 수정 대상.
없음Option<T> — 값이 없는 것이 정상적인 결과. 이유가 필요 없음.
실패Result<T, E> — 예상 가능한 실패. 호출자가 이유를 보고 결정.

?는 "실패면 즉시 반환"을 한 글자로 쓴 것

실패할 수 있는 단계가 여러 개면 match가 중첩되어 코드가 오른쪽으로 밀려납니다. ? 연산자가 이를 해결합니다. expr?는 대략 다음 코드로 펼쳐집니다.

// `let v = expr?;` is roughly: let v = match expr { Ok(v) => v, Err(e) => return Err(From::from(e)), // note the From conversion: see below }; use std::num::ParseIntError; // "id=17;rate=200" -> (17, 200) fn parse_pair(s: &str) -> Result<(u32, u32), String> { let (left, right) = s.split_once(';').ok_or("missing ';'")?; // Option -> Result let id = field(left, "id")?; let rate = field(right, "rate")?; Ok((id, rate)) } fn field(part: &str, key: &str) -> Result { let value = part .strip_prefix(key) .and_then(|rest| rest.strip_prefix('=')) .ok_or_else(|| format!("expected '{key}=...' in {part:?}"))?; value.parse::().map_err(|e: ParseIntError| format!("{key}: {e}")) } fn main() { for input in ["id=17;rate=200", "id=17", "id=x;rate=1", "id=3;speed=9"] { match parse_pair(input) { Ok((id, rate)) => println!("{input:<16} ok id={id} rate={rate}"), Err(e) => println!("{input:<16} err {e}"), } } }

Option에도 ?를 쓸 수 있습니다(함수가 Option을 반환할 때). Option을 Result로 바꿀 때는 ok_or, 그 반대는 .ok()를 씁니다. 위 예제처럼 오류를 String으로 만드는 것은 빠르지만, 호출자가 오류 종류에 따라 다르게 대응할 수 없습니다. 라이브러리라면 오류를 타입으로 설계해야 합니다.

오류를 열거형으로 설계하고 From으로 잇는다

실무 패턴은 이렇습니다. 모듈마다 오류 열거형을 만들고, Display와 std::error::Error를 구현하고, 하위 오류에서 From을 구현합니다. 그러면 ?가 하위 오류를 자동으로 상위 오류로 변환해 줍니다(위 펼침 코드의 From::from(e)).

use std::fmt; use std::num::ParseFloatError; #[derive(Debug)] enum ConfigError { MissingKey(&'static str), BadNumber { key: &'static str, source: ParseFloatError }, OutOfRange { key: &'static str, value: f64, max: f64 }, } impl fmt::Display for ConfigError { fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result { match self { ConfigError::MissingKey(k) => write!(f, "missing key `{k}`"), ConfigError::BadNumber { key, source } => write!(f, "`{key}` is not a number ({source})"), ConfigError::OutOfRange { key, value, max } => write!(f, "`{key}` = {value} exceeds {max}"), } } } impl std::error::Error for ConfigError { fn source(&self) -> Option<&(dyn std::error::Error + 'static)> { match self { ConfigError::BadNumber { source, .. } => Some(source), // keep the cause chain _ => None, } } } struct Limits { max_speed: f64, max_accel: f64 } fn get(text: &str, key: &'static str) -> Result { let line = text.lines() .find_map(|l| l.strip_prefix(key)?.strip_prefix('=')) .ok_or(ConfigError::MissingKey(key))?; line.trim().parse().map_err(|source| ConfigError::BadNumber { key, source }) } fn load(text: &str) -> Result { let max_speed = get(text, "max_speed")?; if max_speed > 2.0 { return Err(ConfigError::OutOfRange { key: "max_speed", value: max_speed, max: 2.0 }); } Ok(Limits { max_speed, max_accel: get(text, "max_accel")? }) } // An application-level error that wraps library errors; `?` converts via From. #[derive(Debug)] enum AppError { Config(ConfigError), Io(String) } impl From for AppError { fn from(e: ConfigError) -> Self { AppError::Config(e) } } fn start(cfg: &str) -> Result<(), AppError> { let lim = load(cfg)?; // ConfigError -> AppError automatically if lim.max_accel <= 0.0 { return Err(AppError::Io("actuator offline".into())); } println!(" started: speed <= {}, accel <= {}", lim.max_speed, lim.max_accel); Ok(()) } fn main() { for cfg in ["max_speed=1.2\nmax_accel=0.5", "max_speed=1.2", "max_speed=fast\nmax_accel=1", "max_speed=3\nmax_accel=1", "max_speed=1\nmax_accel=0"] { println!("{:?}", cfg.replace('\n', "; ")); match start(cfg) { Ok(()) => {} Err(AppError::Config(e)) => { println!(" config error: {e}"); if let Some(cause) = std::error::Error::source(&e) { println!(" caused by: {cause}"); } } Err(AppError::Io(msg)) => println!(" io error: {msg}"), } } }

이 보일러플레이트는 실무에서 크레이트가 대신 써 줍니다. 라이브러리에서는 thiserror로 #[derive(Error)]와 #[error("...")] 속성만 달고, 애플리케이션의 main 근처에서는 anyhow::Result로 아무 오류나 담아 문맥(.context("..."))을 붙여 올립니다. 이 책은 표준 라이브러리만 쓰기 때문에 손으로 썼지만, 구조는 똑같습니다.

// Library crate: precise, matchable errors. #[derive(Debug, thiserror::Error)] pub enum ConfigError { #[error("missing key `{0}`")] MissingKey(&'static str), #[error("`{key}` is not a number")] BadNumber { key: &'static str, #[source] source: std::num::ParseFloatError }, } // Application: any error, with human-readable context. use anyhow::Context; fn main() -> anyhow::Result<()> { let text = std::fs::read_to_string("robot.toml").context("reading robot.toml")?; let _limits = load(&text).context("validating limits")?; Ok(()) }

C 개발자의 눈으로

리눅스 커널 스타일의 "음수 errno 반환 + goto out" 패턴이 하던 일을 Result + ? + Drop이 나눠 맡습니다. 오류 전파는 ?가, 정리는 Drop이 하므로 함수 본문에는 정상 경로만 남습니다. 커널의 Rust 바인딩도 Result<T, kernel::error::Error>로 errno를 감쌉니다.

흔한 함정
  • 라이브러리 함수 안에서 unwrap()/panic!으로 입력 오류를 처리하지 마세요. 호출자는 그 실패를 복구할 기회를 잃습니다.
  • 오류 타입을 String으로 통일하면 호출자가 match할 수 없습니다. 최소한 열거형으로, 그리고 원인(source)을 잃지 마세요.
  • main도 Result<(), E>를 반환할 수 있습니다. Err면 종료 코드 1과 함께 Debug 형식으로 출력됩니다.
