소유권: 값에는 주인이 하나

이 장을 마치면: 소유권 세 규칙을 말할 수 있고, 어떤 대입이 이동(move)이고 어떤 것이 복사(copy)인지 판별할 수 있으며, 값이 언제 해제(drop)되는지 코드만 보고 예측할 수 있습니다.

2장의 정수는 대입하면 복사되는 단순한 값이었습니다. 힙 메모리를 가진 값은 다릅니다. 복사가 비싸고, 무엇보다 "누가 해제할 것인가"라는 질문이 생깁니다. 소유권은 그 질문에 대한 Rust의 답입니다.

세 가지 규칙이 전부다

소유권 규칙
  1. 모든 값에는 소유자(owner)라고 부르는 변수가 하나 있다.
  2. 한 시점에 소유자는 정확히 하나다.
  3. 소유자가 스코프를 벗어나면 값은 해제(drop)된다.

String을 예로 들면, 변수 자체는 스택에 있는 24바이트(64비트 기준) 구조체입니다. 힙 버퍼를 가리키는 포인터, 현재 길이, 용량. 실제 문자 데이터는 힙에 있습니다.

대입은 이동이다: 컴파일러가 이전 이름을 지운다

let s2 = s1;을 C처럼 생각하면 포인터가 두 개가 되어, 둘 다 스코프를 벗어날 때 같은 버퍼를 두 번 해제하는 문제가 생깁니다. Rust는 이 대입을 이동(move)으로 정의합니다. 바이트는 복사되지만 소유권은 s2로 넘어가고, s1은 그 시점부터 쓸 수 없는 이름이 됩니다. 이후 s1을 쓰면 컴파일 오류(E0382)입니다. 런타임 비용은 0이고, 검사는 전부 컴파일 타임에 끝납니다.

fn consume(s: String) -> usize { s.len() } // s is dropped here fn main() { let s1 = String::from("hello"); let s2 = s1; // move: ownership goes to s2 println!("{s2}"); println!("{s1}"); // error[E0382]: borrow of moved value: `s1` let name = String::from("lidar"); let n = consume(name); // passing by value also moves println!("{n} {name}"); // error[E0382] again }

이 예제를 실행해서 메시지를 읽어 보세요. 컴파일러는 "어디서 이동했는지"와 ".clone()을 고려하라"는 제안까지 보여 줍니다. 진짜 복사가 필요하면 clone()을 명시적으로 부릅니다. Rust에서는 비싼 복사가 항상 코드에 드러납니다.

반대로 i32, f64, bool, char, 그리고 이들만으로 된 튜플·배열처럼 힙 자원이 없고 비트 복사가 곧 완전한 복사인 타입은 Copy 트레잇을 구현합니다. Copy 타입의 대입은 이동이 아니라 복사라서 원래 변수를 계속 쓸 수 있습니다.

#[derive(Debug, Clone, Copy)] struct Pose { x: f32, y: f32, theta: f32 } // plain data: can be Copy #[derive(Debug, Clone)] struct Scan { ranges: Vec } // owns heap memory: Clone only fn main() { let p1 = Pose { x: 1.0, y: 2.0, theta: 0.5 }; let p2 = p1; // copy: p1 is still usable println!("{p1:?} {p2:?} heading sum = {}", p1.theta + p2.theta + p1.x * p2.y); let s1 = Scan { ranges: vec![1.2, 1.3, 9.9] }; let s2 = s1.clone(); // explicit deep copy let s3 = s1; // move println!("{:?} {:?}", s2.ranges, s3.ranges); }

Drop은 결정적이고, 역순이다

소유자가 스코프를 벗어나는 순간 컴파일러가 넣어 둔 drop 호출이 실행됩니다. 시점은 GC처럼 "언젠가"가 아니라 코드에서 정확히 보이는 닫는 중괄호입니다. 같은 스코프의 변수는 선언의 역순으로 해제됩니다. 타입에 Drop 트레잇을 구현하면 해제 시점에 원하는 정리 코드를 넣을 수 있고, 이것이 파일·소켓·락을 자동으로 닫는 Rust식 RAII입니다.

struct Tracer(&'static str); impl Drop for Tracer { fn drop(&mut self) { println!(" drop {}", self.0); } } fn make() -> Tracer { let t = Tracer("made in make()"); t // moved out to the caller: NOT dropped here } fn main() { let _a = Tracer("a"); { let _b = Tracer("b"); let _c = Tracer("c"); println!("leaving inner scope"); } // c, then b let m = make(); let moved = m; // moving does not drop anything drop(moved); // std::mem::drop: drop early, explicitly let _ = Tracer("underscore"); // `let _ =` does not bind: dropped immediately println!("end of main"); } // a
C++ 개발자의 눈으로

C++의 std::move는 "옮겨도 된다"는 캐스팅일 뿐이고, 옮겨진 객체는 "유효하지만 지정되지 않은" 상태로 남아 소멸자가 여전히 호출됩니다. Rust의 이동은 파괴적 이동입니다. 옮겨진 쪽은 컴파일러가 이름 자체를 무효화하고 소멸자도 부르지 않습니다. 그래서 이동 생성자를 직접 쓸 일이 없고, use-after-move가 컴파일 오류가 됩니다.

흔한 함정
  • 컴파일 오류를 .clone()으로 덮기: 처음엔 괜찮지만, 큰 버퍼를 루프에서 복제하면 성능이 무너집니다. 대부분은 다음 장의 빌림(&)이 정답입니다.
  • let _guard = lock();과 let _ = lock();은 다릅니다. 후자는 값을 바인딩하지 않아 즉시 drop되므로 락이 바로 풀립니다.
  • Drop 순서에 의존하는 코드(예: 버퍼보다 먼저 닫혀야 하는 핸들)는 필드 선언 순서도 의미가 있습니다. 구조체 필드는 선언 순서대로 drop됩니다.

함수에 값을 넘길 때마다 소유권이 넘어가면 불편합니다. 함수가 잠깐 들여다보기만 하면 되는 경우가 대부분이니까요. 다음 장의 빌림(borrowing)이 그 해법입니다.
