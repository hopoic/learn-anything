오류 처리: 예외·optional·expected

이 장을 마치면: 예외가 던져질 때 스택 되감기와 소멸자가 어떻게 맞물리는지 설명할 수 있고, 예외 안전성 보장 수준과 noexcept를 구분할 수 있으며, 상황에 따라 예외·std::optional·std::expected·assert 중 알맞은 방식을 고를 수 있습니다.

4장의 RAII는 "모든 출구에서 정리한다"고 했습니다. 예외는 그 출구 중 가장 극적인 경우입니다. 이 장에서 RAII가 왜 예외와 한 쌍인지 보게 됩니다.

실행 엔진 안내

이 장의 앞부분 예제는 throw/try를 씁니다. 브라우저 내장 엔진(WASM)은 예외를 지원하지 않으므로, 실행 엔진이 자동이나 온라인으로 설정되어 있어야 합니다. 뒷부분의 optional/expected 예제는 모든 엔진에서 실행됩니다.

C의 오류 처리가 놓치는 것

C에서는 반환값(-1, NULL)과 errno로 실패를 알립니다. 단순하고 비용이 예측 가능하지만 세 가지 약점이 있습니다. 호출자가 검사를 잊어도 컴파일러가 모르고, 오류를 위로 전달하려면 모든 중간 함수가 검사하고 다시 반환해야 하며, 생성자처럼 반환값이 없는 곳에서는 실패를 알릴 방법이 없습니다. C++은 이 문제에 두 가지 답을 줍니다. 제어 흐름을 바꾸는 예외, 그리고 실패를 타입에 담는 결과 타입(optional, expected)입니다.

예외: 던지고, 되감고, 잡는다

throw는 현재 함수를 즉시 빠져나가 호출 스택을 거슬러 올라가며 맞는 catch를 찾습니다. 이 과정이 스택 되감기(stack unwinding)이고, 되감기 중에 지나치는 모든 스코프의 지역 객체는 소멸자가 실행됩니다. 중간 함수들은 오류 검사 코드를 한 줄도 쓰지 않았는데 자원은 하나도 새지 않습니다.

#include #include #include struct Guard { // RAII object to observe unwinding std::string name; explicit Guard(std::string n) : name(std::move(n)) { std::cout << " acquire " << name << '\n'; } ~Guard() { std::cout << " release " << name << '\n'; } }; class SensorError : public std::runtime_error { // derive from the standard hierarchy public: SensorError(const std::string& what, int addr) : std::runtime_error(what), addr_(addr) {} int addr() const { return addr_; } private: int addr_; }; int read_register(int addr) { Guard bus("i2c bus lock"); if (addr == 0x77) throw SensorError("device did not ACK", addr); return addr * 2; } int read_calibration() { Guard buf("dma buffer"); int a = read_register(0x48); // no error checks in between int b = read_register(0x77); // throws return a + b; // never reached } int main() { try { int c = read_calibration(); std::cout << "calibration = " << c << '\n'; } catch (const SensorError& e) { // catch by const reference std::cout << "SensorError: " << e.what() << " at 0x" << std::hex << e.addr() << std::dec << '\n'; } catch (const std::exception& e) { // more general handlers go last std::cout << "other error: " << e.what() << '\n'; } std::cout << "program continues\n"; }

출력에서 release 줄이 언제 찍히는지 보세요. 예외가 read_register에서 출발해 main의 catch에 닿기 전에, 두 Guard가 생성의 역순으로 정리됩니다.

예외 안전성과 noexcept

예외가 지나간 뒤 객체가 어떤 상태로 남는지에 대해 C++은 세 단계의 약속을 씁니다.

기본자원 누수가 없고 불변식이 유지된다. 값은 바뀌었을 수 있다. RAII만 지키면 대부분 자동으로 얻는다.
강한실패하면 호출 전과 완전히 같은 상태. "트랜잭션처럼". 5장의 copy-and-swap 대입이 이 보장을 준다.
nothrow절대 예외를 던지지 않는다. 소멸자, 이동 연산, swap은 이 수준이어야 하고 noexcept로 표시한다.

noexcept는 문서 이상의 의미가 있습니다. 5장에서 본 것처럼 std::vector는 원소의 이동 생성자가 noexcept일 때만 재할당에 이동을 씁니다. 그리고 noexcept 함수에서 예외가 새어 나가면 프로그램은 std::terminate로 즉시 종료됩니다.

C 개발자의 눈으로

주요 구현의 예외는 "제로 비용" 모델입니다. 예외가 던져지지 않는 정상 경로에는 검사 코드가 없고, 대신 되감기 정보 테이블이 바이너리에 들어갑니다. 던질 때는 테이블을 해석하느라 비쌉니다(마이크로초 단위). 그래서 예외는 드문 실패에 쓰고, 흔한 실패에는 아래의 결과 타입을 씁니다. 코드 크기나 결정적 실행 시간이 중요한 펌웨어는 -fno-exceptions로 예외를 아예 끄는 경우가 많습니다.

실패를 값으로: optional과 expected

std::optional<T>(C++17)는 "T 값이 있거나 없거나"입니다. 3장 링 버퍼의 pop()에서 이미 썼습니다. 없는 이유를 알릴 필요가 없을 때 가장 가볍습니다. std::expected<T, E>(C++23)는 "T 값이거나, 실패 이유 E이거나"입니다. 예외처럼 이유를 전달하면서도 제어 흐름은 평범한 반환입니다. 반환 타입에 실패 가능성이 드러나므로 호출자가 무시하기 어렵습니다.

#include #include #include #include #include #include // optional: "maybe there is a value" - no reason needed std::optional find_value(std::string_view line, std::string_view key) { auto pos = line.find(key); if (pos == std::string_view::npos || line.substr(pos + key.size(), 1) != "=") return std::nullopt; auto rest = line.substr(pos + key.size() + 1); return rest.substr(0, rest.find(',')); } // expected: "a value, or the reason why not" enum class ParseError { Empty, NotANumber, OutOfRange }; std::expected parse_int(std::string_view s, int lo, int hi) { if (s.empty()) return std::unexpected(ParseError::Empty); int v = 0; auto [ptr, ec] = std::from_chars(s.data(), s.data() + s.size(), v); // no locale, no exceptions if (ec != std::errc{} || ptr != s.data() + s.size()) return std::unexpected(ParseError::NotANumber); if (v < lo || v > hi) return std::unexpected(ParseError::OutOfRange); return v; } const char* explain(ParseError e) { switch (e) { case ParseError::Empty: return "empty"; case ParseError::NotANumber: return "not a number"; case ParseError::OutOfRange: return "out of range"; } return "?"; } int main() { std::string_view cfg = "baud=115200,retries=x3,timeout=,parity=none"; for (std::string_view key : {"baud", "retries", "timeout", "stopbits"}) { auto raw = find_value(cfg, key); if (!raw) { std::cout << key << ": missing, using default\n"; continue; } auto n = parse_int(*raw, 0, 1'000'000); if (n) std::cout << key << " = " << *n << '\n'; else std::cout << key << ": invalid (" << explain(n.error()) << ")\n"; } // value_or: a default in one call std::cout << "retries or 3: " << parse_int("x3", 0, 10).value_or(3) << '\n'; }

핵심 정리
  • 프로그래머 버그(계약 위반) → assert로 즉시 드러낸다. 복구하지 않는다.
  • 드물고, 여러 층을 건너 처리해야 하는 실패(생성자 실패, 자원 고갈) → 예외.
  • 흔하고, 바로 위 호출자가 처리하는 실패(입력 파싱, 조회 실패) → expected 또는 optional.
  • 어떤 방식이든 RAII가 있어야 누수 없이 동작한다.
